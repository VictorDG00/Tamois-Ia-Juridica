Esquema geral do produto

Esta seção é um resumo executivo — o que o Tamois faz, quais módulos existem e qual o estado atual de cada um.

O que é o Tamois

Tamois é um revisor jurídico com IA. O advogado ou empresário sobe um contrato em DOCX, o sistema analisa automaticamente e devolve:

  • Ficha do contrato — quem contrata quem, valor, prazo, foro, multa (extraídos com IA)
  • Correções ortográficas — erros inequívocos encontrados no texto (ex: "rescição" → "rescisão")
  • Sugestões de redação — trechos ambíguos ou tecnicamente imprecisos com reescrita sugerida
  • Insights jurídicos — riscos classificados por nível (alto / médio / baixo), ancorados no parágrafo de origem
  • DOCX anotado para download — o contrato original com Track Changes e comentários nativos do Word
  • Chat jurídico — o usuário conversa com a IA sobre o documento após a análise

01

Pipeline completo da análise

Quando o usuário faz upload de um DOCX, o sistema percorre 6 etapas encadeadas. A requisição HTTP retorna imediatamente — o processamento pesado roda em background via SolidQueue. São feitas 4 chamadas ao DeepSeek em sequência.

①

Upload e enfileiramento

AnalysesController#create recebe o arquivo, valida o content-type (.docx), cria o registro Analysis com status: "pending", seleciona o modo de análise (fast ou deep) e salva o arquivo via Active Storage (disco local, volume Docker persistente). Enfileira AnalysisJob no SolidQueue e redireciona o usuário imediatamente.

app/controllers/analyses_controller.rb
②

Extração de texto do DOCX

DocxExtractor abre o arquivo DOCX como um ZIP (formato OOXML), lê o XML interno em word/document.xml, extrai todos os parágrafos com Nokogiri e os numera sequencialmente. O texto fica no formato [Paragrafo 0] texto... [Paragrafo 1] texto... para que a IA referencie de onde veio cada problema. O texto extraído é salvo em original_text.

app/services/docx_extractor.rb
③

4 chamadas ao DeepSeek — checkpoints incrementais

AnalysisService chama o DeepseekClient quatro vezes em sequência — uma por seção. Cada chamada tem prompt focado e independente. Entre cada chamada, o resultado parcial é salvo no banco imediatamente, acendendo os checkpoints na tela.

Ordem das chamadas:

  1. 1ª Entidades → extrai ficha do contrato → salva entities_json
  2. 2ª Ortografia → identifica erros inequívocos → salva orthography_json
  3. 3ª Redação → encontra ambiguidades → salva writing_suggestions_json
  4. 4ª Insights jurídicos → classifica riscos → salva legal_insights_json, status → completed

app/services/deepseek_client.rb
④

Persistência e normalização

Cada seção é normalizada antes de salvar: filtra itens inválidos (campos em branco, JSON malformado), valida risk_level nos insights, adiciona disclaimer jurídico automático, trunca campos acima de 600 chars. Os dados ficam como JSON no SQLite. O status muda para "completed" só depois das 4 seções. Em caso de erro, status vai para "failed".

app/models/analysis.rb
⑤

Exibição do resultado

A página analyses/show faz meta-refresh a cada 3 segundos enquanto status != "completed". Ao completar, exibe as 4 seções: ficha do contrato (entidades), ortografia (original/sugestão com diff), redação (trecho + reescrita) e insights jurídicos (ordenados por risco alto→baixo). Cada item tem um botão de feedback para marcá-lo como incorreto.

app/views/analyses/show.html.erb
⑥

Download do DOCX anotado (opcional)

O usuário clica em "Baixar DOCX anotado". A rota GET /analyses/:id/download instancia DocxAnnotator, que abre o DOCX original, aplica Track Changes (ortografia) e comentários de margem (redação + insights) diretamente no XML, e devolve o arquivo para download sem modificar o original armazenado.

app/services/docx_annotator.rb
02

Como extraímos o texto do DOCX

Um arquivo .docx é um ZIP disfarçado. Dentro dele existe uma estrutura de arquivos XML que segue o padrão OOXML (Office Open XML). O documento de texto fica em word/document.xml.

Estrutura interna de um DOCX
contrato.docx (ZIP)
├── word/
│ ├── document.xml  ← texto principal está aqui
│ ├── styles.xml
│ ├── comments.xml  ← comentários (gerado pelo DocxAnnotator)
│ └── _rels/document.xml.rels  ← relacionamentos (patched)
├── [Content_Types].xml  ← patched para incluir comments
└── _rels/
O que o DocxExtractor faz
# 1. Abre o DOCX como ZIP
Zip::File.open(file_path) do |zip|
  xml = zip.find_entry("word/document.xml").get_input_stream.read
end

# 2. Lê o XML com Nokogiri
doc = Nokogiri::XML(xml)
NS = { "w" => "http://schemas.openxmlformats.org/wordprocessingml/2006/main" }

# 3. Extrai todos os parágrafos <w:p> e os numera
paragraphs = doc.xpath("//w:p", NS).map.with_index do |para, idx|
  text = para.xpath(".//w:t", NS).map(&:text).join(" ").strip
  text.empty? ? nil : "[Paragrafo #{idx}] #{text}"
end.compact

# Resultado — texto indexado enviado ao DeepSeek (máx. 20.000 chars)
# "[Paragrafo 0] CONTRATO DE PRESTAÇÃO DE SERVIÇOS"
# "[Paragrafo 1] As partes abaixo qualificadas celebram..."
💡

A indexação [Paragrafo N] é fundamental: o DeepSeek retorna o paragraph_id nos insights jurídicos, indicando de qual parágrafo veio cada risco. Isso permite ao DocxAnnotator ancorar o comentário exatamente no parágrafo correto ao gerar o DOCX anotado.

03

As 4 chamadas ao DeepSeek

Fazemos 4 chamadas HTTP separadas à API do DeepSeek — uma por seção. Cada chamada tem um prompt focado em uma única tarefa, com temperatura 0.1 (conservador). O modelo varia conforme o modo escolhido.

Modelos disponíveis
ModoModeloVelocidadeProfundidade
Rápido (fast) deepseek-chat 15–40s por seção Boa para a maioria dos casos
Profundo (deep) deepseek-reasoner 30–90s por seção Raciocínio em cadeia — melhor para contratos complexos
As 4 seções — o que cada prompt pede
Chamada 1 Entidades (ficha do contrato)

"Extraia as informações-chave deste contrato. Copie EXATAMENTE o que está no texto. Se não encontrar, retorne null. NUNCA invente, NUNCA infira." Campos: contratante · contratada · objeto · valor · vigencia · prazo_pagamento · multa · foro.

Chamada 2 Ortografia

"Analise APENAS erros ortográficos e gramaticais inequívocos. NÃO reporte: jargão jurídico, latinismos, termos técnicos, variações aceitas, palavras corretas em contexto jurídico." Retorna orthography.

Chamada 3 Redação

"Analise APENAS problemas de redação jurídica: ambiguidade semântica, contradições lógicas, imprecisão que gera insegurança jurídica. NÃO reporte erros ortográficos (tratados na chamada anterior). Use 'excerpt' com o trecho EXATO do texto." Retorna writing_suggestions.

Chamada 4 Insights jurídicos

"Analise APENAS riscos baseados em norma jurídica específica e identificável. NÃO reporte especulações ou riscos hipotéticos. Classifique: high (nulidade, inconstitucionalidade), medium (cláusula abusiva confirmada), low (imprecisão terminológica). Inclua paragraph_id." Retorna legal_insights.

⚠️

Regra fundamental anti-alucinação — presente em todos os prompts: "Só reporte itens com CERTEZA ABSOLUTA. Em caso de dúvida, não reporte. Prefira lista pequena e precisa a lista grande com itens duvidosos."

04

Como pegamos e validamos o retorno

O DeepSeek retorna um JSON dentro de uma resposta de API padrão. Extraímos, limpamos e validamos antes de salvar — modelos de linguagem às vezes retornam JSON malformado, com markdown ao redor, ou campos em branco.

Pipeline de validação do retorno
# 1. Extrai o content da resposta
content = body.dig("choices", 0, "message", "content")

# 2. Remove markdown se o modelo colocou ```json ... ```
clean = strip_markdown(content)

# 3. Tenta parsear o JSON — fallback extrai o { } mais externo
parsed = JSON.parse(clean)

# 4. Normalização por seção:
# entities: valida 8 campos, null para ausentes, máx 200 chars
# orthography: exige 'original' e 'suggestion' não vazios
# writing: exige 'excerpt' e 'suggestion' não vazios
# insights: exige 'topic' e 'insight', valida risk_level,
# fallback 'medium' para level inválido, paragraph_id >= 0

# 5. Insights ganham disclaimer automático (máx total 600 chars)
insight_text = "#{insight_content} #{DISCLAIMER}"

05

DOCX anotado para download

✅

Implementado e em produção. O DocxAnnotator gera o DOCX anotado em memória — o arquivo original nunca é modificado. Rota: GET /analyses/:id/download.

O documento final abre no Word (ou Google Docs) com as correções e comentários nativos — como se um revisor humano tivesse trabalhado no documento.

✏️

Correções ortográficas → Track Changes (rastreamento nativo)

Cada erro ortográfico vira uma revisão nativa do Word: o texto errado aparece tachado em vermelho e o correto sublinhado em verde, com o revisor "Tamois" registrado. O usuário aceita ou rejeita cada correção individualmente.

O algoritmo localiza a palavra dentro dos nós <w:r> do XML, divide o run se necessário, e insere os nós <w:del> e <w:ins> com IDs únicos.

Implementação: <w:del w:author="Tamois"> + <w:ins w:author="Tamois">

💬

Sugestões de redação → Comentários de margem

O parágrafo onde o excerpt foi encontrado é ancorado com commentRangeStart/End. Na margem direita aparece um balão com: ícone 💬, trecho original, sugestão e motivo. O usuário decide se aceita e reescreve manualmente.

Implementação: <w:commentRangeStart>/<w:commentRangeEnd> + entrada em word/comments.xml

⚖️

Insights jurídicos → Comentários com nível de risco

Cada insight é ancorado diretamente pelo paragraph_id que a IA retornou. O comentário começa com o emoji do risco (🔴 ALTO, 🟡 MÉDIO, 🟢 BAIXO) e o tópico em destaque, seguido da análise completa com o disclaimer jurídico.

Fallback: se paragraph_id inválido, busca o parágrafo pelo início do topic (primeiros 20 chars)

Como o OOXML de Track Changes funciona

<!-- Track Change: "rescição" → "rescisão" -->
<w:p>
  <w:r><w:t xml:space="preserve">O contrato prevê a </w:t></w:r>

  <!-- Texto REMOVIDO (tachado vermelho no Word) -->
  <w:del w:id="1" w:author="Tamois" w:date="2026-05-19">
    <w:r><w:delText>rescição</w:delText></w:r>
  </w:del>

  <!-- Texto INSERIDO (sublinhado verde no Word) -->
  <w:ins w:id="2" w:author="Tamois" w:date="2026-05-19">
    <w:r><w:t>rescisão</w:t></w:r>
  </w:ins>

  <w:r><w:t xml:space="preserve"> do contrato.</w:t></w:r>
</w:p>

Como os comentários de margem funcionam

<!-- Em word/document.xml — ancora o comentário no parágrafo -->
<w:p>
  <w:commentRangeStart w:id="10"/>
  <w:r><w:t>A parte contratante poderá rescindir...</w:t></w:r>
  <w:commentRangeEnd w:id="10"/>
  <w:r><w:commentReference w:id="10"/></w:r>
</w:p>

<!-- Em word/comments.xml — conteúdo do balão -->
<w:comment w:id="10" w:author="Tamois" w:date="2026-05-19" w:initials="T">
  <w:p><w:pPr><w:pStyle w:val="CommentText"/></w:pPr>
    <w:r><w:t>🔴 RISCO HIGH — Cláusula de Responsabilidade</w:t></w:r></w:p>
  <w:p><w:r><w:t>Isenção ilimitada pode ser abusiva (CDC art. 51)...</w:t></w:r></w:p>
</w:comment>

Chat jurídico e sistema de feedback

Chat jurídico por análise

Como funciona o chat

Após a análise, o usuário acessa o chat via GET /analyses/:id/chat. O DeepSeek recebe um system prompt com o resumo da análise + até 160.000 chars do documento original, e os últimos 10 turnos do histórico de mensagens.

# System prompt do chat:
"Você é Tamois, um assistente jurídico especializado em direito brasileiro.
Resumo: X correções, Y sugestões, Z insights (N de alto risco).
Trecho do documento: [primeiros 160.000 chars do original_text]"

# + histórico dos últimos 10 turnos + pergunta atual do usuário
# temperatura: 0.5 (mais conversacional que a análise)

Sistema de feedback

Cada item exibido na tela de resultado tem um botão para o usuário sinalizar que a análise está incorreta. O feedback é salvo com um snapshot do item no momento do clique — útil para identificar padrões de erros do modelo e calibrar os prompts.
